# Immune Cell Trial Analysis — Loblaw Bio

Interactive dashboard and analysis pipeline for Bob Loblaw's clinical trial, exploring how miraclib affects immune cell populations in melanoma patients.

---

## Quick Start (GitHub Codespaces)

```bash
make setup      # Install dependencies
make pipeline   # Load DB + run all analysis (Parts 1–4)
make dashboard  # Start dashboard → see URL instructions below
```

---

## Dashboard

### Accessing in GitHub Codespaces

After running `make dashboard`, the app starts on port 8050. To get the public URL:

1. In Codespaces, click the **Ports** tab at the bottom panel (next to Terminal)
2. Find port **8050** — click the 🌐 globe icon to open it in your browser
3. The URL will look like:
   `https://<your-codespace-name>-8050.app.github.dev`

> **Note:** The port must be set to **Public** visibility (right-click → Port Visibility → Public) for the link to be shareable. By default Codespaces ports are private.

### Running locally

```bash
make dashboard
# Visit http://localhost:8050
```

**Tabs:**
- **Frequency Overview** — Box plots of relative frequency distributions per cell population with interactive sample/population/percentage filters. The chart aggregates all selected samples together.
- **Statistical Analysis** — Grouped box plots (responders vs non-responders) + Mann-Whitney U statistical table + key findings.
- **Subset Analysis** — KPI cards (avg B cells, qualifying samples), samples-per-project bar chart, responder and sex distribution pie charts.

## Database Schema

### Design

Three normalized tables:

```
subjects
  subject_id  TEXT  PK
  project     TEXT
  condition   TEXT
  age         INTEGER
  sex         TEXT
  treatment   TEXT
  response    TEXT

samples
  sample_id                 TEXT  PK
  subject_id                TEXT  FK → subjects
  sample_type               TEXT
  time_from_treatment_start INTEGER

cell_counts
  id          INTEGER  PK (autoincrement)
  sample_id   TEXT     FK → samples
  population  TEXT
  count       INTEGER
```

### Rationale

**Why normalize?** The raw CSV repeats subject-level metadata (age, sex, treatment, response) on every sample row. Splitting into `subjects`, `samples`, and `cell_counts` eliminates that redundancy and makes the data easier to maintain and query.

**Why long/tidy format for cell_counts?** Storing one row per `(sample, population)` pair rather than one wide row per sample means:
- Adding a new cell population requires no schema change, just new rows.
- Aggregations (sum by population, filter by population) are natural SQL queries.
- Indexes on `sample_id` and `population` keep queries fast.

**Scalability (hundreds of projects, thousands of samples):**
- The three-table schema handles growth gracefully — each new sample adds a few rows to `samples` and five rows to `cell_counts`.
- Indexes on foreign keys and `population` ensure that JOIN-heavy analytical queries (e.g., average frequency of B cells across all PBMC samples at baseline) remain efficient.
- For very large datasets (millions of rows), the same schema works in PostgreSQL with minimal migration effort; the long format is also directly compatible with columnar stores (Parquet, BigQuery) used in data warehouse analytics.
- Multi-project analytics (e.g., cross-project batch effects) are simple `GROUP BY project` queries.

## Code Design

| File | Role |
|------|------|
| `load_data.py` | Single-responsibility: schema creation + CSV ingestion. Idempotent (drops and recreates DB each run). |
| `analysis.py` | Modular functions per part (`run_part2`, `run_part3`, `run_part4`). Each saves its own output to `outputs/`. |
| `dashboard.py` | Dash app with three tabs, one per analysis part. Queries the DB directly so it always reflects the latest data. |

The pipeline and dashboard are deliberately decoupled: `make pipeline` runs headlessly and generates all output files, while `make dashboard` is only needed for interactive exploration.
